# Public Lead Capture: MVP Implementation Gate

Status: implemented and verified locally; production migration, push, and
deployment remain unapplied.

## Current defect

The generated customer-site forms in `webstaffr/templates/site/home.html`,
`contact.html`, and `service.html` submit to `POST /intake`. That endpoint is
the NetBuild.Pro business-onboarding API and requires a complete
`IntakeRequest`; the public forms send only visitor contact fields. A real
visitor submission therefore fails validation and creates no customer lead.

The static artifact generator in `webstaffr/site_magic_engine.py` has the same
contract mismatch. Existing `webstaffr_leads` rows belong to Leo's B2B sales
scoring workflow and have no service-request or source-page fields. Reusing
that table would mix two different lead types and discard the visitor's actual
request.

## Recommended MVP contract

Add one purpose-built public endpoint:

`POST /sites/{tenant_id}/leads`

Request fields:

- `name`: required, trimmed, 1-120 characters
- `phone`: optional, 3-40 characters
- `email`: optional, valid email, at most 254 characters
- `message`: required, trimmed, 1-2,000 characters
- `service`: optional, at most 160 characters
- `source_path`: optional, server-normalized to the tenant's site routes
- `website`: hidden honeypot; a non-empty value is accepted without storing a
  lead so basic bots cannot distinguish the rejection

At least one of `phone` or `email` is required. The `tenant_id` comes only from
the URL. The server verifies that the tenant and site exist before writing.

Success response: HTTP 201 with an opaque `lead_id` and `status: "received"`.
The browser then renders a local confirmation without navigating away. The
response must not reveal tenant configuration, routing, CRM state, or whether
an external sync succeeded.

## Required persistence

Create a dedicated `website_leads` table rather than altering Leo's scoring
table:

- `lead_id`: UUID/text primary key generated by the application
- `tenant_id`: non-null foreign key to `tenants(tenant_id)`, cascade delete
- `name`, `phone`, `email`, `message`, `service`, `source_path`
- `ghl_contact_id`: provider contact reference retained for reconciliation
- `status`: `received`, `forwarded`, or `forward_failed`; default `received`
- `forward_attempts`: non-negative integer; default 0
- `last_forward_error_code`: safe category only, never raw provider text
- `created_at`, `updated_at`

Index `(tenant_id, created_at)`. PostgreSQL RLS must be enabled with no public
policies, matching the current server-held trusted connection model. SQLite
and PostgreSQL migration artifacts must be reviewed together and applied to
production only under a separate production-schema approval.

The next available local migration number is `0015`; the PostgreSQL manual
sequence already includes `0017_customer_auth_rls.sql`, so the corresponding
PostgreSQL table/RLS migration must use `0018`. The application should generate
opaque UUID lead IDs itself, avoiding any `lastrowid` dependency or Postgres
shim change.

## Security and reliability requirements

- Apply request-body limits already enforced by the application middleware.
- Rate-limit independently by tenant and direct client IP. Never trust caller
  forwarding headers until a trusted-proxy policy exists.
- Validate the requested `service` against that tenant's published services or
  store it as null; never accept it as authorization or routing authority.
- Escape all confirmation output and never reflect arbitrary form values.
- Commit the local lead before any GHL forwarding attempt.
- Treat GHL forwarding as best effort. An absent or failing GHL integration
  leaves the lead persisted with `forward_failed`; it must not turn a valid
  visitor submission into a lost lead or HTTP 500.
- Run synchronous provider calls outside the async event loop. Attribute every
  GHL source and note to the exact tenant and business so a shared NetBuild.Pro
  CRM location does not erase lead provenance.
- Preserve an upserted GHL contact ID when a later note write fails, allowing
  deterministic reconciliation without creating another contact.
- Log tenant ID, opaque lead ID, outcome, and safe error category only. Do not
  log contact details or message bodies.
- The endpoint is already inside the existing `/sites/` public CORS prefix;
  add regression coverage rather than broadening global CORS.
- Custom-domain middleware must pass `/sites/{tenant_id}/leads` through as an
  API path. It now rewrites only site-page GET/HEAD routes, so assets, Angel
  chat, health, onboarding, and lead submission keep their original paths.

## UI changes after approval

- Point all three Jinja forms and generated artifact forms to the new endpoint.
- Add a message textarea and preserve the current service as a hidden field on
  service pages.
- Submit with progressively enhanced JavaScript so keyboard-only and
  no-JavaScript visitors still receive a usable confirmation response.
- Use truthful copy: “Request received” after HTTP 201. Do not promise a
  response time, appointment, price, or 24/7 availability unless supplied by
  tenant data.

## Acceptance evidence

Implementation is not complete until tests prove:

1. valid home, contact, and service submissions return 201 and persist every
   field under the URL tenant;
2. unknown and malformed tenant IDs write nothing;
3. a service from another tenant is rejected or stored as null;
4. phone/email minimum contact validation and all length bounds hold;
5. honeypot submissions write nothing;
6. rate limits cover both tenant and direct client IP;
7. one tenant cannot retrieve or mutate another tenant's lead;
8. GHL absent/failure still preserves the local lead with a safe status;
9. CORS is present only for approved public origins/routes;
10. rendered forms no longer reference the onboarding `/intake` endpoint;
11. full pytest and `scripts/health_check.py` pass.

## External activation boundary

The local `website_leads` schema, endpoint, forms, and tests described above are
implemented. Applying `0018_website_leads.sql` to Supabase, pushing, deploying,
adding credentials, or forwarding real customer data to GHL are external live
actions and remain unapplied.

Local verification at completion: 43 focused lead/GHL tests passed, health
10/10, and the full suite passed 542 tests with 51 subtests and one third-party
Starlette/httpx deprecation warning.
