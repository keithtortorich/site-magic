# ADR-030: Demo Sites via SiteMagic

**Date:** 2026-08-10  
**Status:** Phase 1 implemented, uncommitted (see TASKS.md 2026-08-10 entry for what shipped and what's still gated on a live SiteMagic worker)  
**Author:** Engineering  
**Stakeholders:** Founder (UX/marketing direction), sales team (prospect demos)

---

## Problem Statement

Demo sites linked from the agency site (`/demos/{slug}`) currently serve static fixtures rendered through the real `site_render_router`. This means:

1. **Demos don't reflect the actual SiteMagic output.** Prospects see placeholder HTML, not what a real customer's generated site looks like after the full pipeline.
2. **Demos can drift from reality.** A SiteMagic update (new design, styling, schema changes) is invisible to demos until someone manually re-renders fixtures.
3. **Demo verification is manual.** There's no automated pipeline verifying demos stay current with SiteMagic output.

**Desired outcome:** Demo sites are generated by SiteMagic, so they always reflect what customers will get. The agency site links to live SiteMagic output, proving the product works.

---

## Solution: Demo Jobs on First Access

### Architecture

Demo sites are **internal SiteMagic jobs** with reserved tenant IDs:

1. **Reserved tenant IDs** for demos:
   - `_demo_hvac`, `_demo_plumbing`, `_demo_roofing`, `_demo_water_restoration`, `_demo_garage_door`, `_demo_pest_control`, `_demo_landscaping`, `_demo_tree_service`, `_demo_cleaning`
   - Leading underscore marks them as system-reserved (never user-created)
   - Stored in a new enum `DemoTrade` in `site_magic.py`

2. **Demo data source:**
   - A new `demo_sites.py` file (same as before) defines fixtures: `IntakeSubmissionData` for each trade
   - Keyed by slug (`hvac`, `plumbing`, etc.), maps to reserved tenant ID and verified-facts payload
   - No database changes needed — demos are transient, enqueued on demand

3. **Demo site routes at `/demos/{slug}`:**
   - **First access:** Check if a completed SiteMagic job exists for that demo's reserved tenant ID
   - **If not:** Enqueue a new SiteMagic job with source type `intake`, source payload from `demo_sites.py`
   - **If in progress:** Poll and serve a "building" placeholder
   - **If complete:** Redirect or proxy to the real `/sites/{reserved_tenant_id}/web` route
   - **If failed:** Log error, serve a static fallback ("demo build failed, try again")

4. **Integration points:**
   - New `demo_router.py` handles `/demos/*` routes
   - New `DemoJobManager` class wraps SiteMagic job lifecycle (enqueue, poll, serve)
   - Reuses existing `SiteMagicQueue`, `SiteMagicRepository`, `site_render_router` — no new SiteMagic logic
   - Registered in `create_app()` like any other router

5. **Demo banner & isolation:**
   - Existing `is_demo: bool` context flag (from STANDUP) gates a banner on each demo page
   - Reserved tenant ID in routing ensures a real tenant's data never mixes with demo content
   - Test: a real tenant at slug `hvac` cannot collide with `_demo_hvac`

### Data Flow

```
GET /demos/hvac
  ↓
demo_router.py: lookup "hvac" → _demo_hvac reserved tenant_id
  ↓
DemoJobManager: check SiteMagicRepository for completed job at (_demo_hvac, status=ready_for_review)
  ├─ If exists: proxy to /sites/_demo_hvac/web
  ├─ If in progress: render "building..." page
  ├─ If failed: render fallback + log error
  └─ If not found: enqueue new job via site_magic_queue with intake fixture
       → POST /site-magic/jobs {tenant_id: _demo_hvac, source_type: intake, verified_facts: {...}}
       → worker picks up → SiteMakerEngine.run() → publishes → demo_router serves it
```

### Demo-Specific Behavior

- **No form submission:** Demo `/book` and `/contact` forms show "This is a sample site" message (existing, per STANDUP)
- **No database writes:** Jobs are ephemeral; completed jobs live only in the SiteMagic schema
- **No time limit:** A demo job is valid indefinitely until re-built
- **Stale demo rebuild:** Manual via `/api/internal/demo-rebuild/{slug}` (admin-only, optional feature for later)

## Implementation Phases

### Phase 1: Demo Job Manager + Router (this PR)
- `demo_sites.py` — fixture definitions (same as before)
- `demo_job_manager.py` — `DemoJobManager` class:
  - `enqueue_if_needed(reserved_tenant_id, demo_fixture) -> job_id`
  - `poll_status(reserved_tenant_id) -> {"status": "ready_for_review"|"building"|"failed", ...}`
  - `get_preview_url(reserved_tenant_id) -> str`
- `demo_router.py` — HTTP routes:
  - `GET /demos/{slug}` — demo home page (proxies to generated site)
  - `GET /demos/{slug}/...` — other demo pages (about, contact, services, etc.)
  - `GET /demos` — gallery index (list of demo slugs with links)
  - `GET /demo-api/status/{slug}` — JSON status (for front-end polling during build)
- Update `app.py` — include `demo_router`, wire `DemoJobManager` with real `SiteMagicQueue`
- Tests:
  - Demo fixture shape (required fields, no unsupported claims)
  - Job enqueue on first access
  - Poll status (building → ready_for_review)
  - Proxy to rendered site
  - "Demo" banner on demo pages, absent on real tenant pages
  - Old URLs still redirect (301 from `/demo-sites/hvac.html` to `/demos/hvac`)

### Phase 2: Stale Demo Rebuild (optional, post-MVP)
- Manual endpoint: `POST /internal/demo-rebuild/{slug}` (X-API-Key auth)
- Deletes or marks old job, enqueues fresh rebuild
- Useful for pushing demo changes without waiting for organic traffic

### Phase 3: Automated Demo Health Check (optional, post-MVP)
- Add to `health_check.py`: rebuild any demo older than X days
- Ensures demos stay fresh and SiteMagic is exercised regularly

## Constraints & Tradeoffs

| Constraint | Why | Implication |
|---|---|---|
| Reserved tenant IDs (`_demo_*`) | Prevents collision with real tenants | Demo routes are deterministic, always serve the same content until explicitly rebuilt |
| No form submission on demos | Prevents demo leads flooding CRM | Prospects know it's a sample (banner) before they try to submit |
| Jobs live only in SiteMagic DB | No additional storage layer | Demos are rebuilt from fixtures if the job record is ever deleted (safe, but lossy) |
| Enqueue on first access, not cold-start | Keeps boot time fast | First visitor pays the build latency; subsequent visitors get cached result |

---

## Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Demo build fails, prospect sees error | Graceful fallback: serve static HTML or "demo unavailable, try again" + log the error + alert ops |
| Demo job clogs the worker queue | Demos are 1–2% of volume; separate demo-job priority (optional); worker has backpressure by design |
| SiteMagic update breaks a demo | Demo rebuild auto-runs on health check or manual trigger; test suite runs all 9 demos before merge |
| Reserved tenant ID accidentally used by real user | Validation in `IntakeRepository.create()`: reject any tenant_id starting with `_` (or whitelist only alphanumeric) |

- Run all 9 demos through SiteMagic pipeline (part of pre-merge verification gates)
- Verify each demo renders without errors
- Check demo banner is gated correctly

### Health Check
- Add new check: all 9 demos have a completed job in the last X days
- Alert if any demo build is missing or stale

## Rollout & Rollback

### Rollout
1. Implement Phase 1 (job manager + router)
2. Test against staging SiteMagic queue
3. Deploy with feature flag (demo jobs enqueued only if `DEMO_SITES_VIA_SITEMAGIC=true`)
4. Monitor first few builds, check for errors
5. Flip flag to `true` after stable

### Rollback
- Set `DEMO_SITES_VIA_SITEMAGIC=false` → routes fall back to static fixtures (if fixtures still exist on disk)
- Or: simple code revert (no schema changes, no migrations)
